# DemoExam Control Center

Веб-дашборд для подготовки и проведения демонстрационного экзамена на кластере Proxmox VE. Он объединяет сценарии развёртывания, жизненный цикл стендов, автопроверки и оценку нагрузки экзаменационных VM.

[Посмотреть обзор кластера на демоданных](docs/deployer-overview.webp)

## Возможности

- создание, редактирование, дублирование, публикация и удаление сценариев;
- выбор QEMU-шаблона в сценарии; количество VM, подсеть и bridge задаются отдельно при каждом развёртывании;
- редактирование bootstrap- и autocheck-скриптов прямо в браузере;
- фоновое пакетное развёртывание стенда с созданием Proxmox pool, linked clone VM, bootstrap и автоматическим snapshot `start`;
- фоновый возврат к snapshot `start` для одной VM, всего выбранного стенда или всех подходящих стендов с повторным запуском и сохранением текущих паролей;
- подключение уже существующего Proxmox pool к мониторингу и сценарию без повторного клонирования VM;
- запуск, остановка и перезапуск всех VM стенда;
- создание снимка и смена пароля как на всех VM, так и на одной выбранной машине;
- отдельные логин/пароль каждой VM, массовое копирование доступов и переход в её web UI по адресу `https://IP:8006`;
- быстрое пакетное управление питанием и удаление стенда вместе с его VM, дисками и pool;
- запуск автопроверки для всего стенда или отдельной VM, подсчёт результата и хранение истории;
- встроенный IPAM: атомарное резервирование адресов, защита от дублей и просмотр занятости;
- живое обновление прогресса развёртывания и автопроверки в открытой карточке без скачков прокрутки;
- мониторинг CPU, RAM и диска кластера, нод и отдельно VM, относящихся к экзаменационным стендам;
- оценка недавней активности во вложенных Proxmox web UI по журналам `pveproxy` внутри стендов;
- журнал действий и адаптивный интерфейс без отдельной сборки frontend.

## Быстрый запуск

Требуется Python 3.10 или новее. Для демонстрационного режима внешние Python-пакеты не нужны.

```console
python server.py
```

Откройте <http://127.0.0.1:8080>. При первом запуске будет создана SQLite-база `data/dashboard.db` с демонстрационными сценариями, стендами и результатами проверок.

Параметры командной строки:

```console
python server.py --host 127.0.0.1 --port 8080 --db data/dashboard.db
```

- `--host` — адрес прослушивания, по умолчанию `127.0.0.1`;
- `--port` — порт, по умолчанию `8080`;
- `--db` — путь к SQLite, по умолчанию `data/dashboard.db`.

Остановка сервера: `Ctrl+C`.

## Практикум: личные стенды и выдача учёток

**Картинки в задании.** В редакторе сценария поставьте курсор в текст Markdown и нажмите **«Загрузить изображение»** либо вставьте скриншот через **Ctrl+V**. Поддерживаются PNG, JPEG и WebP; браузер подгоняет размер для загрузки. В квадратных скобках вставленной ссылки можно изменить подпись. До 12 разных картинок на задание. Картинки сохраняются в Deployer, без внешнего хостинга; до публикации доступны только преподавателю. После снятия публикации студенческая ссылка больше не выдаёт файл. Экспорт задания в Markdown или автономный JSON не включает сами файлы изображений.

**Как добавить задание.** Откройте **Сценарии → Создать сценарий** или отредактируйте существующий сценарий. Укажите название (его увидят студенты), выберите шаблон VM и заполните **Задание для студентов** в Markdown. Заголовки, списки, таблицы, цитаты, ссылки и блоки кода можно проверить в предпросмотре. Сам Markdown — только условие работы: он не выполняется в VM и не заменяет bootstrap или автопроверку.

Для публикации выберите статус **Активен**, включите **Показывать задание студентам** и сохраните. До этого можно сохранять черновик. Новые, ранее существовавшие и дублированные сценарии не публикуются автоматически. Изменения попадают в личные студенческие кабинеты без экспорта или перезапуска. Если снять галочку, новые запуски по этому заданию блокируются, текст скрывается даже в прежней карточке, но уже выданная VM не выключается. В открытой вкладке изменения видны при следующем обновлении (обычно до 30 секунд); скачанный студентом файл отозвать нельзя. Публичная демоучётка показывает отдельные примеры, а не материалы преподавателя.

В админке откройте отдельную страницу **Обучение → Учётки студентов** (`/#student-accounts`). Найти учётку можно по логину или группе, а список отсортировать по логину либо по названию группы в обоих направлениях. Чтобы выдать доступы, нажмите **Создать учётки группы**, введите группу, количество (от 1 до 100; по умолчанию 20) и при необходимости префикс логинов. Скопируйте выданные пары до ухода со страницы. Пароли кабинета не выводятся повторно; в базе хранятся только их солёные хеши. Повторный выпуск продолжает нумерацию, не меняя прежние пароли. Передавайте каждому студенту только его строку. Создание группы **не запускает VM**.

**Если студент потерял пароль**, в том же разделе найдите его по логину или группе, откройте управление и сбросьте пароль. Скопируйте новый пароль до закрытия окна и передайте лично студенту. Старый пароль и все прежние сеансы кабинета сразу станут недействительными. Там же можно отдельно завершить все сеансы, заблокировать вход или разблокировать учётку. Сброс пароля сам по себе не снимает блокировку. Управление относится к выданным учёткам, а не к встроенным профилям `student01` и `student02`. Эти действия не меняют пароль внутри Proxmox, не закрывают уже открытый там сеанс и не удаляют стенд или задания студента.

В списке **Группа** выберите группу, указанную при создании учёток: останутся только её студенты. Поиск и сортировка действуют внутри выбранной группы. Пункт **Все группы** снимает фильтр. Первый столбец **ID** — постоянный номер учётки, начиная с 0: он не зависит от выбранной группы, поиска или страницы и не выдаётся повторно после удаления.

**История входов** показывает преподавателю время последних 50 успешных входов студента в учебный кабинет. Она не включает неудачные попытки или входы во вложенный Proxmox. До появления истории сохранялось только время последнего входа, поэтому более старых событий нет.

**Удаление учётки** требует ввести её точный логин. Оно удаляет учётные данные и историю входов, прекращает сеансы кабинета и сохраняет логин в списке недоступных для повторной выдачи. Выданная VM в Proxmox не удаляется и не передаётся следующему студенту; при необходимости преподаватель отдельно освобождает её через **Стенды**. Для временного запрета входа используйте блокировку, а не удаление.

Студент входит в `/student-demo/` с выданными данными, выбирает опубликованное задание и нажимает **Развернуть стенд**. Срок задаётся в минутах перед запуском; пустое поле означает бессрочный стенд. В рабочем режиме Deployer создаёт отдельный пул и одну VM по сценарию через обычную очередь Proxmox. Кабинет показывает состояние этой заявки. После готовности студент может открыть вложенный Proxmox и скопировать **гостевой** пароль — это не пароль кабинета.

За студентом закрепляется один стенд за раз. Повторный клик или вход из другой вкладки не создаёт ещё один клон. При перегрузке преподаватель подтверждает продолжение в админке Deployer. Остановка по таймеру не удаляет работу. Чтобы дать студенту другое задание с новой VM, преподаватель сначала освобождает прежний стенд в Deployer; чужая или повторно импортированная VM студенту не выдаётся. Для старого вручную привязанного пилота действует описанный ниже порядок отзыва.

**Сеть и включение на сервере.** Нужны live-режим Proxmox, настроенный `DASHBOARD_ADMIN_TOKEN`, актуальный каталог сценариев и выделенный интервал внутри `10.39.0.0/16`. Укажите включительно первый и последний адрес в `STUDENT_LAB_IP_START` и `STUDENT_LAB_IP_END`. Без этих параметров новые реальные VM не запускаются. При выдаче IPAM пропускает занятые записи и не выходит за последний адрес. Зарезервируйте этот интервал и в DHCP или внешнем IPAM, если ими пользуетесь: выключенные и не учтённые Deployer машины не обязаны отвечать на ping.

Чтобы подобрать интервал на хосте demoex, выполните из каталога проекта:

```console
python -m dashboard_backend.student_range --source-db /var/lib/demoexam-dashboard/dashboard-live.db --probe
```

Утилита читает IPAM, записи VM и локальную таблицу соседей. С флагом `--probe` дополнительно проверяет выбранных кандидатов ICMP-запросами; без флага трафик в сеть не отправляется. Она только предлагает интервал, не меняет настройки и не создаёт VM. После сверки перенесите `start` и `end` в указанные выше переменные окружения веб-сервиса.

### Автономное демо и ранее созданный пилот

В меню Deployer выберите **Обучение → Кабинет студента · демо**. Кабинет можно запустить и отдельно, без настройки Proxmox, административного сервера или токена:

```console
python student_demo.py
```

Откройте [кабинет на localhost](http://127.0.0.1:8081/student-demo/). На экране входа нажмите на демологин, затем «Войти в кабинет».

| Профиль | Демоучётка | Пароль |
| --- | --- | --- |
| Алина, ДЭ-24 | `student01` | `DemoLab01!` |
| Максим, ДЭ-25 | `student02` | `DemoLab02!` |

Выберите практическую работу, нажмите **Развернуть стенд** и дождитесь окончания подготовки. В карточке личного стенда можно открыть инструкцию, пройти по её шагам и скачать задание в TXT. После выхода и повторного входа стенд сохраняется. Попробуйте одно и то же задание под обоими профилями: экземпляры будут разными, а повторный запуск у того же студента не создаст дубль.

По умолчанию это симуляция: студенческая кнопка не клонирует VM, не выдаёт сетевые адреса и не запускает учебную ОС. Формулировки заданий — примеры для демонстрации, а не содержимое гостевых машин. Сессии и учебные экземпляры живут в отдельной SQLite-базе `student-demo-state.db`. Два публичных демопрофиля предназначены для показа, а не для выдачи реальным студентам. Не открывайте студентам административный сайт и не раздавайте им пароли reverse proxy.

**Вход во вложенный Proxmox.** В рабочем кабинете с привязкой к реальной VM `student01` входит по личному паролю, а не по публичному демопаролю. Преподаватель может скопировать его в разделе **Стенды → нужная VM → Скопировать пароль кабинета** и передать студенту лично. Если код задания уже выдавался, он и есть пароль кабинета. После обновления старой демосессии потребуется один новый вход; сам стенд сохранится. В карточке задания кнопка **Скопировать пароль** сразу копирует пароль вложенного Proxmox: вводить код ещё раз не нужно. Рядом доступны **Скопировать логин** и **Открыть мой Proxmox**.

**Сеть студенческих VM.** Для нового реального стенда с владельцем вида `student01` сервер принимает только `10.39.0.0/16`. Указывайте выделенный стартовый адрес (например, `10.39.4.0/16`): IPAM сохраняет его хостовую часть и пропускает адреса, уже занятые в Deployer. Адрес сети без конкретного старта не используется для автоматической выдачи адреса возможного шлюза. При привязке проверяются также префикс IPAM и адрес с маской внутри гостя.

**Срок работы.** В мастере развёртывания нового управляемого пула можно указать от 1 до 10 080 минут. Пустое поле оставляет стенд бессрочным. Реальный таймер начинается после готовности VM, переживает перезапуск Deployer и инициирует штатное выключение только изначально созданных VM. Добавленные вручную машины, диски и снимки не удаляются. Для существующего личного пилота можно однократно назначить срок прямо в карточке задания по личному коду — тогда отсчёт идёт с подтверждения. Срок демосимуляции не выключает реальную VM; импортированные и общие пулы не получают таймер.

Для привязки используйте новый управляемый пул с одной VM и закреплённым в IPAM адресом. Оператор размещает рядом с базой файл `student-pilot-request.json`: ровно `student_login`, `assignment_id`, `stand_id` (ID студенческой карточки), `guest_ipv4`, `deployer_stand_id` (числовой ID в админке) и `pool_id`. Файл должен быть доступен сервису для чтения, но недоступен для записи группе и остальным. Паролей в файле нет. Пока VM не готова, карточка сообщает об ожидании и не показывает ссылку.

После **успешного** штатного развёртывания сервис проверяет зарезервированный адрес, пул и сам HTTPS-интерфейс внутри гостя. Только затем создаётся `student-pilot.json` с дополнительным полем `vmid` — ID клона. Подтверждённая привязка не перезаписывается автоматически. При изменении или исчезновении записи VM из инвентаря ссылка скрывается. Для отзыва через карточку уберите оба файла; это не отзывает уже выданный гостевой пароль — его меняют отдельно. Остановка кластера, снятие ограничений очереди и выдача доступа к основной панели Proxmox для пилота не требуются.

Если очередь поставила развёртывание на паузу, дождитесь освобождения ресурсов и подтвердите **повторный запуск того же стенда** в админке; новую заявку создавать не нужно. Если VM уже запущена, но гостевой `pveproxy` поднялся с задержкой и ссылка не появилась, оператор может повторить только проверку в серверном окружении Deployer: `python -m dashboard_backend.student_pilot_publish --source-db /var/lib/demoexam-dashboard/dashboard-live.db --stand-id ID`. Эта команда не клонирует, не запускает и не выключает VM.

**Экспорт только для автономного примера.** Встроенный кабинет Deployer читает публикации из базы сценариев. В отдельном `student_demo.py` без каталога используются демонстрационные задания. При необходимости преподаватель может экспортировать материалы для автономного показа:

```console
python student_demo.py --refresh-catalog --source-db /var/lib/demoexam-dashboard/dashboard-live.db --catalog /var/lib/demoexam-dashboard/student-demo-catalog.json
```

Команда записывает в JSON только опубликованные задания активных сценариев с подтверждённым QEMU-шаблоном, включая текст Markdown, без скриптов или паролей. Для автономного запуска передайте `--catalog путь/к/student-demo-catalog.json`. Это отдельная копия для демонстрации: после редактирования или снятия задания с публикации обновите экспорт, если продолжаете раздавать его отдельно.

## Режимы Proxmox

### Demo

Это режим по умолчанию (`PROXMOX_MODE=demo`). Он не подключается к Proxmox и безопасен для знакомства с интерфейсом:

- развёртывание и управляющие операции имитируются;
- VMID и адреса генерируются локально;
- график содержит синтетические данные за 24 часа;
- смена пароля, снимки и удаление не затрагивают реальную инфраструктуру.

### Live

Live-режим выполняет реальные операции в Proxmox. Установите `proxmoxer`:

```console
python -m pip install proxmoxer
```

Пример запуска из PowerShell:

```powershell
$env:PROXMOX_MODE = "live"
$env:PROXMOX_HOST = "pve.example.com"
$env:PROXMOX_PORT = "8006"
$env:PROXMOX_USER = "dashboard-api@pve"
$env:PROXMOX_TOKEN_NAME = "dashboard"
$env:PROXMOX_TOKEN_VALUE = "новый-секрет-токена"
$env:PROXMOX_VERIFY_SSL = "true"
$env:DASHBOARD_ADMIN_TOKEN = "длинный-случайный-токен-оператора"
python server.py
```

Токен Proxmox должен принадлежать отдельной служебной учётной записи с минимально необходимыми ACL. Для работы нужны права на чтение ресурсов кластера, создание и удаление pool, клонирование и настройку QEMU VM, управление питанием и снимками, включая `VM.Snapshot.Rollback`, доступ к task API и QEMU Guest Agent. Для выполнения bootstrap, автопроверки и чтения журнала web-активности требуется `VM.GuestAgent.Unrestricted`; для запуска VM после отката — `VM.PowerMgmt`. Не выдавайте токену глобальные административные права без необходимости.

Live-развёртывание:

1. Создаёт отдельный Proxmox pool.
2. Находит QEMU-шаблон по `template_vmid`.
3. Проверяет storage шаблона. Для linked clone целевая нода должна видеть как base-диск, так и созданный overlay. Если общее storage нельзя надёжно подтвердить, все VM остаются на ноде шаблона.
4. Среди совместимых нод выбирает наименее загруженные и пакетами создаёт VM как linked clone. Если bridge не указан, сетевой адаптер сохраняется из шаблона; унаследованный флаг Proxmox `link_down` всегда снимается.
5. Параллельно выполняет Bash- или PowerShell bootstrap внутри гостевых ОС. Для сетевого Linux-bootstrap применяет конфигурацию через `ifreload` и требует, чтобы гостевой интерфейс был `UP` с точным назначенным IPv4. Если live-применение не помогло, автоматически один раз перезагружает только проблемную VM и повторяет проверку.
6. Только после готовности сети генерирует отдельный пароль каждой VM, устанавливает его через QEMU Guest Agent и создаёт snapshot `start`.
7. При ошибке пытается удалить уже созданные VM. Pool удаляется только после подтверждённой очистки; иначе он сохраняется для повтора удаления из карточки стенда.

В шаблоне должен быть установлен и запущен QEMU Guest Agent. Скрипт развёртывания получает переменные `STAND_NAME`, `STAND_POOL`, `VM_INDEX`, `VMID`, `VM_IP`, `STAND_SUBNET` и `VM_BRIDGE`.

### Если развёртывание ждёт решения

На странице **«Стенды»** откройте карточку со статусом **«Ждёт решения»**. Deployer показывает причину до создания первого клона. Заявка сохраняет исходный сценарий, пул и зарезервированные IP даже после перезапуска сервиса.

- **«Повторить запуск»** заново проверяет нагрузку. Если ресурсы уже освободились, оставьте список стендов пустым.
- Если нужны ресурсы, отметьте стенды, про которые вы знаете, что работа закончена, и подтвердите выключение. В списке только управляемые стенды текущей рабочей области без обнаруженной веб-активности за последние 15 минут. Проверка использует журнал вложенного Proxmox и может пропустить работу в открытой консоли. Перед выключением Deployer повторяет проверку. Если гостевая ОС не подтвердила штатное завершение работы, заявка снова ждёт решения. Уже выключенные VM остаются выключенными.
- **«Удалить задачу»** снимает заявку и освобождает адреса IPAM. Если заявка ждёт решения, пул и диски Proxmox удалять не требуется.

Если у операции уже есть UPID, откройте в Proxmox окно **Tasks → нужная задача → Output**. На узле, указанном в UPID, те же данные доступны через `pvenode task list --source active`, `pvenode task status '<UPID>'` и `pvenode task log '<UPID>'`. Проверьте последнюю запись и состояние операции до повторного запуска клонирования. Пауза Deployer действует до отправки операции в Proxmox.

Параметры режима и HTTP-сервера (они также есть в `.env.example`):

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `PROXMOX_MODE` | `demo` или `live` | `demo` |
| `PROXMOX_CLUSTER_NAME` | отображаемое имя live-кластера | `Proxmox VE` |
| `DASHBOARD_HOST` | адрес HTTP-сервера, если не передан `--host` | `127.0.0.1` |
| `DASHBOARD_PORT` | порт HTTP-сервера, если не передан `--port` | `8080` |
| `DASHBOARD_ADMIN_TOKEN` | защита изменяющих API и чтения паролей VM | пусто |

Если `DASHBOARD_ADMIN_TOKEN` задан, frontend передаёт его из `localStorage` в заголовке `X-Admin-Token`. При первом ответе `401` дашборд сам откроет защищённую форму ввода; позже токен можно заменить нажатием на профиль «Администратор» в правом верхнем углу. Для автоматизированной настройки также подходит консоль браузера:

```javascript
localStorage.setItem("demoops.adminToken", "тот-же-токен");
location.reload();
```

Обычные GET-маршруты открыты, но `/credentials` и `/api/web-activity` требуют этот токен. Для доступа по сети закройте весь сайт аутентификацией reverse proxy, добавьте HTTPS и firewall. Без `DASHBOARD_ADMIN_TOKEN` изменяющие запросы, чтение паролей и web-активности разрешены, поэтому такой запуск допустим только на localhost.

## Сценарии и автопроверки

Сценарий содержит выбранный QEMU-шаблон, bootstrap и отдельный autocheck-скрипт. Количество VM, начальный IPv4 с префиксом и bridge выбираются в мастере развёртывания; тип клона фиксирован как linked clone. Сохранённый код привязан к сценарию; стенд запускает актуальную версию автопроверки своего сценария.

Поле IPAM сохраняет адресную часть введённого CIDR. Поэтому `10.39.4.0/16` начинает выдачу с `10.39.4.0`, а не с нормализованного `10.39.0.0`. Пропускаются только настоящий адрес сети, broadcast и уже занятые адреса. Резервации создаются одной транзакцией до фонового клонирования, поэтому параллельные запросы не получают одинаковые IP. Ошибочный стенд сохраняет резервации до удаления, чтобы адрес случайно не был выдан работающей VM; при удалении стенда они освобождаются автоматически.

В редакторе bootstrap доступна кнопка **«Вставить из vklvikl»**. Она восстанавливает сетевой Linux-скрипт из исходного `vklvikl.py`: назначает переданный `VM_IP`, берёт префикс из `STAND_SUBNET`, обновляет `/etc/hosts` и без отключения интерфейса применяет конфигурацию через `ifreload`. Для старого `ifupdown` вместо потенциально конфликтного live-переключения backend автоматически один раз перезагружает только эту VM. По умолчанию используются гостевой интерфейс `vmbr0` и gateway `10.39.1.1`; их можно переопределить переменными `GUEST_INTERFACE` и `VM_GATEWAY`. Backend дополнительно проверяет `UP`, активный bridge-порт и единственный точный IP даже у ранее сохранённых сценариев со старой версией скрипта. Пароль `root` и snapshot `start` создаются только после этой проверки.

**Создание снимка.** Кнопки снимка отдельной VM и всего стенда возвращают управление сразу после постановки задачи в очередь (HTTP 202). Можно закрыть карточку. Счётчик готовых VM растёт только после успешного завершения соответствующей задачи Proxmox. Снимки сохраняют диски и конфигурацию; оперативная память не включается. Время записи зависит от хранилища. Результат записывается в журнал, а в карточке видно, сколько VM успели завершить снимок даже при частичной ошибке.

В строке каждой VM доступна кнопка **«Вернуть к start»**, а в общих действиях карточки — **«Вернуть к изначальному состоянию»** для всех VM выбранного стенда. На странице **«Стенды»** кнопка **«Вернуть все стенды к start»** запускает ту же процедуру для всех подходящих управляемых стендов; импортированные pools, занятые стенды и объекты без готового snapshot или сохранённого пароля безопасно пропускаются. После подтверждения dashboard откатывает машины пакетами, запускает их, ждёт QEMU Guest Agent и повторно применяет сохранённые текущие пароли. Результаты прежней автопроверки сбрасываются как устаревшие. Операция удаляет все дисковые и конфигурационные изменения после `start` и выполняется в фоне со статусом «Восстанавливается». Если QEMU Guest Agent не подтвердил восстановление пароля отдельной VM, dashboard скрывает этот пароль как недостоверный, но сохраняет его внутри для безопасного повторного запуска операции.

На странице **«Стенды»** кнопка **«Добавить существующий pool»** показывает pools из Proxmox, которые ещё не закреплены за стендами. При подключении выбирается сценарий, а найденные QEMU VM добавляются в мониторинг нагрузки и становятся доступны для действий стенда. Удаление такого подключения удаляет только запись дашборда: исходный pool, VM и диски в Proxmox сохраняются.

В live-режиме Deployer примерно раз в 30 секунд читает состав подключённых пулов через Proxmox API. Добавленная вручную QEMU VM появляется в разделе **«Дополнительные VM в пуле»** открытой карточки с именем, VMID, узлом и состоянием. Для чтения состава токену нужен доступ `Pool.Audit` к соответствующему пулу. Обычные действия стенда охватывают только закреплённые за ним машины. Отдельная команда **«Удалить все стенды»** у импортированного пула показывает полный список VMID, включая ручные VM, и запрашивает новое подтверждение, если состав успел измениться.

В мастере **«Развернуть новый стенд»** можно включить **«Добавить в существующий pool»** и выбрать свободный Proxmox pool из списка. Deployer создаст в нём только новые VM стенда с уникальными именами. При удалении такого стенда удаляются только созданные им VM; сам pool и существовавшие в нём ресурсы сохраняются. Если галочка выключена, мастер создаёт новый pool с указанным названием.

Фоновая синхронизация выполняется раз в 30 секунд без пересоздания страницы. Пока открытая карточка показывает развёртывание или автопроверку, она опрашивает только этот стенд примерно раз в секунду, незаметно обновляет прогресс и сохраняет прокрутку. Кнопка **«Обновить»** немедленно перерисовывает текущую страницу.

В live-режиме код передаётся через QEMU Guest Agent и выполняется **внутри гостевой VM**, а не на сервере дашборда:

- PowerShell определяется по заголовку и характерным конструкциям;
- остальные скрипты запускаются через `bash`;
- bootstrap имеет таймаут 900 секунд на VM;
- автопроверка имеет таймаут 180 секунд на VM и получает `VMID`;
- результаты каждой VM объединяются в один запуск.

Рекомендуемый формат stdout автопроверки — JSON, один объект на строку:

```json
{"name":"Служба DNS","ok":true,"message":"named active"}
{"name":"Маршрут","ok":false,"message":"default route missing"}
```

Также поддерживаются JSON-массив и короткие значения `name:ok`, `name:passed`, `name:fail`, `name:failed`, `name:error`. Итоговый статус: `passed` при результате от 90%, `warning` от 70%, иначе `failed`.

Скрипты считаются доверенным административным кодом. Встроенной песочницы, проверки синтаксиса и согласования изменений нет. Не помещайте в них токены, пароли и другие секреты: текст сценариев хранится в SQLite без шифрования.

## Как устроены метрики

В разделе **Наблюдение → Потребители ресурсов** (`/#consumers`) можно сравнивать все видимые в Proxmox гостевые VM и контейнеры независимо от пулов и рабочих областей Deployer. Рейтинг CPU отражает фактически используемые ядра, RAM — показания Proxmox, а размер диска — ёмкость корневого образа, не занятые блоки. Дисковый I/O и сетевой трафик считаются по разности байтовых счётчиков между двумя замерами. Первый замер или отсутствующие счётчики не интерпретируются как нулевая нагрузка. Отдельно показаны узлы, заполненность хранилищ и рекомендации с цифрами; автоматически конфигурация кластера не меняется.

Отчёт читает `GET /cluster/resources` только по запросу и не чаще раза в 15 секунд для всех операторов вместе. Права служебной учётной записи определяют видимость (`VM.Audit`, `Sys.Audit`, `Datastore.Audit`); отсутствие объекта в списке не доказывает его отсутствие в кластере. При сбое последний замер помечается как устаревший, а через пять минут вместо него возвращается ошибка. Подробнее о значениях полей — в [описании API Proxmox](https://pve.proxmox.com/pve-docs/api-viewer/#/cluster/resources).

В live-режиме backend получает `/cluster/resources` и сопоставляет ресурсы с VMID из таблицы `stand_vms`:

- общая CPU, RAM и disk-нагрузка вычисляется по ресурсам нод;
- экзаменационная нагрузка — сумма потребления работающих VM, принадлежащих управляемым стендам;
- `exam_cpu`, `exam_ram` и `exam_disk` показывают долю полной ёмкости кластера;
- `exam_*_share` показывает долю экзаменационных VM в текущем общем потреблении;
- по каждой ноде возвращаются общая нагрузка, вклад экзаменационных VM и их количество.

История live-метрик хранится только в памяти процесса: максимум 120 образцов, новый образец появляется при запросе метрик и исчезает после перезапуска. Результат `/cluster/resources` кэшируется на 5 секунд; при стандартном невидимом опросе frontend раз в 30 секунд история охватывает примерно час. В demo-режиме возвращается синтетический 24-часовой ряд.

Атрибуция является оценкой по телеметрии VM. Нагрузку гипервизора, общий page cache, shared storage, сетевую инфраструктуру и часть фонового I/O нельзя строго отнести к конкретному стенду. Значения CPU в карточках отдельных стендов сейчас хранятся в SQLite и не пересчитываются из Proxmox непрерывно; для оперативной картины используйте кластерные и понодовые показатели.

На странице **«Инфраструктура»** карточка **«Веб-активность на стендах»** раз в 30 секунд читает последние строки `/var/log/pveproxy/access.log` через QEMU Guest Agent и показывает VM, IP клиента, пользователя и время последнего регулярного запроса интерфейса. Для этого API-токену требуется право `VM.GuestAgent.Unrestricted`, а Guest Agent должен работать внутри каждой проверяемой VM. Это именно оценка недавней активности, а не точный счётчик сессий: Proxmox не хранит серверный список открытых вкладок, несколько вкладок объединяются, за reverse proxy виден его адрес, а пользователи за одним NAT и общей учётной записью неразличимы. Такой же запрос может выполнить API-клиент, поэтому запись не доказывает присутствие конкретного человека.

## Смена пароля стенда

Операция `rotate_password` доступна для запущенного стенда или отдельной VM и вызывает `set-user-password` QEMU Guest Agent. При deploy для каждой VM генерируется отдельный 8-символьный пароль без визуально похожих символов `0/O/o` и `1/I/i/l/L`. Dashboard не вводит минимальный лимит для заданного вручную непустого пароля; максимальная длина 1024 символа определяется штатным API Proxmox. Системный пользователь по умолчанию — `root`, логин вложенного Proxmox web UI — `root@pam`.

Чтобы доступ можно было открыть после перезапуска dashboard, пароль хранится в SQLite и выдаётся только через защищённые маршруты `/credentials`. Обычные ответы `/stands` его не содержат, а тела ответов не логируются встроенным сервером. Ограничьте права на файл базы (`chmod 600 data/dashboard.db`), обязательно задайте `DASHBOARD_ADMIN_TOKEN`, используйте HTTPS и не логируйте тела ответов на reverse proxy.

Кнопка **«Перейти к стенду»** показывает трёхшаговый вход. Сначала оператор открывает адрес VM и один раз вручную принимает самоподписанный сертификат. Затем dashboard может отправить логин и пароль непосредственно в штатный HTML login endpoint этой VM, после чего интерфейс открывается с установленной Proxmox-сессией. Логин и пароль также копируются раздельно как надёжный запасной вариант; секреты не помещаются в URL.

Нативную страницу браузера **«Принять риск»** нельзя нажать из JavaScript. Старый `vklvikl` обходил её локальным Selenium с `--ignore-certificate-errors`, но серверный dashboard не управляет браузером оператора. Для полностью прозрачного одношагового входа установите доверенные сертификаты на вложенные Proxmox либо используйте отдельный reverse proxy/auth-bridge с DNS-именами стендов.

## Безопасность и ротация старого токена

Прежний API-токен находился непосредственно в исходном скрипте. Считайте его скомпрометированным, даже если файл больше не содержит секрета:

1. Создайте новый токен для отдельной служебной учётной записи и выдайте минимальные ACL.
2. Передайте новый секрет через `PROXMOX_TOKEN_VALUE`; не записывайте его в код, README или `.env.example`.
3. Запустите live-режим и проверьте `GET /api/health`.
4. Сразу отзовите старый токен в Proxmox: удалите его в `Datacenter → Permissions → API Tokens`.
5. Если секрет попадал в Git, артефакты CI, резервные копии или логи, очистите историю/артефакты и запустите secret scanning. Простого удаления строки из текущей версии недостаточно.

Дополнительные рекомендации:

- оставляйте `PROXMOX_VERIFY_SSL=true`; для собственного CA установите доверенный корневой сертификат на host дашборда;
- не публикуйте встроенный HTTP-сервер напрямую в интернет;
- используйте reverse proxy с HTTPS, полной аутентификацией и ограничением по сети;
- задавайте длинный случайный `DASHBOARD_ADMIN_TOKEN` и периодически меняйте его;
- не коммитьте рабочий `.env`, SQLite-базу, выгрузки паролей и логи;
- проверяйте deploy/autocheck-код перед публикацией сценария;
- перед удалением стенда убедитесь, что pool и VMID принадлежат именно ему: операция удаляет VM и диски без корзины.

## Основные API-маршруты

API принимает и возвращает JSON. Тело запроса должно быть JSON-объектом и не может превышать 2 МиБ. Если задан `DASHBOARD_ADMIN_TOKEN`, все `POST`, `PATCH`, `DELETE` и GET-маршруты `/credentials` требуют заголовок `X-Admin-Token`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | состояние сервера и интеграции Proxmox |
| `GET` | `/api/bootstrap` | все данные, необходимые frontend при загрузке |
| `GET` | `/api/overview` | сводные показатели |
| `GET` | `/api/metrics` | кластерные, понодовые и экзаменационные метрики |
| `GET` | `/api/resource-consumers` | потребители ресурсов всего видимого кластера и рекомендации; требует административный токен, если он настроен |
| `GET` | `/api/web-activity` | недавняя активность во вложенных Proxmox web UI; защищено административным токеном |
| `GET` | `/api/activity?limit=30` | последние события, максимум 100 |
| `GET`, `POST` | `/api/blueprints` | список и создание сценария |
| `GET`, `PATCH`, `DELETE` | `/api/blueprints/{id}` | чтение, изменение и удаление сценария |
| `POST` | `/api/blueprints/{id}/duplicate` | создание черновой копии |
| `GET`, `POST` | `/api/stands` | список и запуск развёртывания стенда |
| `POST` | `/api/stands/actions` | массовый `rollback_start_all` для подходящих стендов |
| `GET` | `/api/pools` | доступные Proxmox pools и состояние их подключения |
| `GET` | `/api/ipam` | сводка, диапазоны и адресные резервации IPAM |
| `POST` | `/api/pools/import` | подключение существующего pool как стенда |
| `GET`, `PATCH`, `DELETE` | `/api/stands/{id}` | детали, изменение метаданных и удаление стенда |
| `POST` | `/api/stands/{id}/actions` | `start`, `stop`, `restart`, `snapshot`, `rollback_start`, `rotate_password`, `run_check`. Для ожидающей заявки — `retry_deploy` с необязательным массивом `stop_stand_ids` или `cancel_deploy` |
| `GET` | `/api/stands/{id}/relief-candidates` | стенды рабочей области без обнаруженной веб-активности, защищено административным токеном |
| `GET` | `/api/stands/{id}/credentials` | защищённые доступы всех VM стенда |
| `POST` | `/api/stands/{id}/vms/{vmid}/actions` | `snapshot`, `rollback_start`, `rotate_password` или `run_check` одной VM |
| `GET` | `/api/stands/{id}/vms/{vmid}/credentials` | защищённый доступ одной VM |
| `GET` | `/api/checks` | история автопроверок |
| `POST` | `/api/checks/run` | запуск проверки; тело `{"stand_id": 1}` |

Ошибки имеют форму `{"error":"описание","code":"validation_error"}`. Основные HTTP-статусы: `400` для неверных данных, `401` для административного токена, `404` для отсутствующего объекта, `409` для конфликта состояния и `500` для ошибки backend/Proxmox.

## Ограничения текущей версии

- Встроенный `ThreadingHTTPServer` предназначен для локальной эксплуатации и пилота; в production нужен reverse proxy, TLS и внешняя аутентификация.
- Полноценной модели пользователей и ролей dashboard пока нет. Административный токен защищает изменения и чтение паролей, но не остальные данные.
- Demo seed добавляется только в режиме `demo`; новая live-база начинается пустой, чтобы синтетические VMID не могли пересечься с реальными гостями.
- После рестарта Deployer восстанавливает новую заявку со сохранённым планом и запрашивает подтверждение. Если процесс уже перешёл к выполнению операции Proxmox или у старой заявки нет сохранённого плана, прерванное live-развёртывание получает статус `error`. Перед повтором такого развёртывания проверьте существующие задачи и VM. Незавершённые автопроверки помечаются отдельно.
- Стенды бессрочные: автоматическая остановка или удаление по TTL намеренно отсутствует.
- Поддерживается развёртывание QEMU VM; LXC-сценарии в новом gateway не реализованы.
- QEMU Guest Agent обязателен для bootstrap, автопроверки, смены пароля и оценки web-активности.
- Пакетные операции над несколькими VM не атомарны. Перед `rollback_start` snapshot проверяется у всего стенда, но runtime-ошибка Proxmox всё равно может оставить часть уже откатившихся VM; dashboard покажет это как ошибку и не снимает защитные lock вручную.
- История live-метрик не сохраняется в SQLite и не является системой долговременного мониторинга.
- Редактор скриптов не предоставляет sandbox, lint, approval workflow и полноценную историю версий.
- Автовход через штатный HTML endpoint требует, чтобы сертификат VM уже был принят браузером и браузер разрешил её session cookie. Для гарантированного одношагового SSO нужен внешний auth-bridge или общий доверенный PKI.
- Web-активность определяется по периодическим запросам UI в `pveproxy/access.log`; она не является точным реестром браузерных сессий и не различает вкладки или пользователей с одинаковыми IP и логином.
