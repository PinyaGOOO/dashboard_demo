# DemoExam Control Center

Веб-дашборд для подготовки и проведения демонстрационного экзамена на кластере Proxmox VE. Он объединяет сценарии развёртывания, жизненный цикл стендов, автопроверки и оценку нагрузки экзаменационных VM.

## Возможности

- создание, редактирование, дублирование, публикация и удаление сценариев;
- выбор QEMU-шаблона в сценарии; количество VM, подсеть и bridge задаются отдельно при каждом развёртывании;
- редактирование bootstrap- и autocheck-скриптов прямо в браузере;
- фоновое пакетное развёртывание стенда с созданием Proxmox pool, linked clone VM, bootstrap и автоматическим snapshot `start`;
- фоновый возврат всех VM стенда к snapshot `start` с повторным запуском и сохранением текущих паролей;
- подключение уже существующего Proxmox pool к мониторингу и сценарию без повторного клонирования VM;
- запуск, остановка и перезапуск всех VM стенда;
- создание снимка и смена пароля как на всех VM, так и на одной выбранной машине;
- отдельные логин/пароль каждой VM, массовое копирование доступов и переход в её web UI по адресу `https://IP:8006`;
- быстрое пакетное управление питанием и удаление стенда вместе с его VM, дисками и pool;
- запуск автопроверки для всего стенда или отдельной VM, подсчёт результата и хранение истории;
- встроенный IPAM: атомарное резервирование адресов, защита от дублей и просмотр занятости;
- живое обновление прогресса развёртывания и автопроверки в открытой карточке без скачков прокрутки;
- мониторинг CPU, RAM и диска кластера, нод и отдельно VM, относящихся к экзаменационным стендам;
- журнал действий и адаптивный интерфейс без отдельной сборки frontend.

## Быстрый запуск

Требуется Python 3.10 или новее. Для демонстрационного режима внешние Python-пакеты не нужны.

```console
python server.py
```

Откройте <http://127.0.0.1:8080>. При первом запуске будет создана SQLite-база `data/dashboard.db` с демонстрационными сценариями, стендами и результатами проверок.

Параметры командной строки:

```console
python server.py --host 127.0.0.1 --port 8080 --db data/dashboard.db
```

- `--host` — адрес прослушивания, по умолчанию `127.0.0.1`;
- `--port` — порт, по умолчанию `8080`;
- `--db` — путь к SQLite, по умолчанию `data/dashboard.db`.

Остановка сервера: `Ctrl+C`.

## Режимы Proxmox

### Demo

Это режим по умолчанию (`PROXMOX_MODE=demo`). Он не подключается к Proxmox и безопасен для знакомства с интерфейсом:

- развёртывание и управляющие операции имитируются;
- VMID и адреса генерируются локально;
- график содержит синтетические данные за 24 часа;
- смена пароля, снимки и удаление не затрагивают реальную инфраструктуру.

### Live

Live-режим выполняет реальные операции в Proxmox. Установите `proxmoxer`:

```console
python -m pip install proxmoxer
```

Пример запуска из PowerShell:

```powershell
$env:PROXMOX_MODE = "live"
$env:PROXMOX_HOST = "pve.example.com"
$env:PROXMOX_PORT = "8006"
$env:PROXMOX_USER = "dashboard-api@pve"
$env:PROXMOX_TOKEN_NAME = "dashboard"
$env:PROXMOX_TOKEN_VALUE = "новый-секрет-токена"
$env:PROXMOX_VERIFY_SSL = "true"
$env:DASHBOARD_ADMIN_TOKEN = "длинный-случайный-токен-оператора"
python server.py
```

Токен Proxmox должен принадлежать отдельной служебной учётной записи с минимально необходимыми ACL. Для работы нужны права на чтение ресурсов кластера, создание и удаление pool, клонирование и настройку QEMU VM, управление питанием и снимками, включая `VM.Snapshot.Rollback`, доступ к task API и QEMU Guest Agent. Для запуска VM после отката также требуется `VM.PowerMgmt`. Не выдавайте токену глобальные административные права без необходимости.

Live-развёртывание:

1. Создаёт отдельный Proxmox pool.
2. Находит QEMU-шаблон по `template_vmid`.
3. Проверяет storage шаблона. Для linked clone целевая нода должна видеть как base-диск, так и созданный overlay. Если общее storage нельзя надёжно подтвердить, все VM остаются на ноде шаблона.
4. Среди совместимых нод выбирает наименее загруженные и пакетами создаёт VM как linked clone. Если bridge не указан, сетевой адаптер сохраняется из шаблона; унаследованный флаг Proxmox `link_down` всегда снимается.
5. Параллельно выполняет Bash- или PowerShell bootstrap внутри гостевых ОС. Для сетевого Linux-bootstrap применяет конфигурацию через `ifreload` и требует, чтобы гостевой интерфейс был `UP` с точным назначенным IPv4. Если live-применение не помогло, автоматически один раз перезагружает только проблемную VM и повторяет проверку.
6. Только после готовности сети генерирует отдельный пароль каждой VM, устанавливает его через QEMU Guest Agent и создаёт snapshot `start`.
7. При ошибке пытается удалить уже созданные VM. Pool удаляется только после подтверждённой очистки; иначе он сохраняется для повтора удаления из карточки стенда.

В шаблоне должен быть установлен и запущен QEMU Guest Agent. Скрипт развёртывания получает переменные `STAND_NAME`, `STAND_POOL`, `VM_INDEX`, `VMID`, `VM_IP`, `STAND_SUBNET` и `VM_BRIDGE`.

## Переменные окружения

`server.py` читает переменные процесса и **не загружает `.env` автоматически**. `.env.example` — только безопасный шаблон для process manager, контейнера, CI/CD или ручной установки переменных.

Параметры подключения Proxmox:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `PROXMOX_HOST` | DNS-имя или IP Proxmox API без схемы и пути | нет; обязательна в live |
| `PROXMOX_PORT` | порт Proxmox API; для reverse proxy без порта в URL обычно используется `443` | `8006` |
| `PROXMOX_USER` | служебный пользователь, например `dashboard-api@pve` | нет; обязательна в live |
| `PROXMOX_TOKEN_NAME` | имя API-токена | нет; обязательна в live |
| `PROXMOX_TOKEN_VALUE` | секрет API-токена | нет; обязательна в live |
| `PROXMOX_VERIFY_SSL` | проверка TLS-сертификата (`true`/`false`) | `true` |
| `PROXMOX_HOSTS` | список нод через запятую для совместимости с legacy-интеграциями | пусто; dashboard сейчас не использует |
| `PROXMOX_CLONE_BATCH` | одновременно запущенные задачи linked clone, от 1 до 12 | `6` |
| `PROXMOX_DEPLOY_WORKERS` | параллельные bootstrap/QGA-операции, от 1 до 12 | `6` |
| `PROXMOX_SNAPSHOT_BATCH` | одновременно создаваемые snapshots, от 1 до 12 | `6` |
| `PROXMOX_ROLLBACK_BATCH` | одновременно откатываемые к `start` VM, от 1 до 12 | `4` |
| `PROXMOX_DELETE_BATCH` | одновременно удаляемые VM, от 1 до 12 | `6` |
| `PROXMOX_GUEST_INTERFACE` | интерфейс внутри Linux VM для штатного bootstrap из vklvikl | `vmbr0` |
| `PROXMOX_NETWORK_READY_TIMEOUT` | ожидание сети после однократной автоматической перезагрузки VM, секунд | `180` |
| `STAND_WEB_SCHEME` | схема web UI вложенного стенда | `https` |
| `STAND_WEB_PORT` | порт web UI вложенного стенда; пустая строка убирает порт | `8006` |
| `STAND_WEB_URL_TEMPLATE` | необязательный шаблон URL с подстановкой `{ip}` | пусто |

Параметры режима и HTTP-сервера (они также есть в `.env.example`):

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `PROXMOX_MODE` | `demo` или `live` | `demo` |
| `PROXMOX_CLUSTER_NAME` | отображаемое имя live-кластера | `Proxmox VE` |
| `DASHBOARD_HOST` | адрес HTTP-сервера, если не передан `--host` | `127.0.0.1` |
| `DASHBOARD_PORT` | порт HTTP-сервера, если не передан `--port` | `8080` |
| `DASHBOARD_ADMIN_TOKEN` | защита изменяющих API и чтения паролей VM | пусто |

Если `DASHBOARD_ADMIN_TOKEN` задан, frontend передаёт его из `localStorage` в заголовке `X-Admin-Token`. При первом ответе `401` дашборд сам откроет защищённую форму ввода; позже токен можно заменить нажатием на профиль «Администратор» в правом верхнем углу. Для автоматизированной настройки также подходит консоль браузера:

```javascript
localStorage.setItem("demoops.adminToken", "тот-же-токен");
location.reload();
```

Обычные GET-маршруты открыты, но `/credentials` требует этот токен. Для доступа по сети закройте весь сайт аутентификацией reverse proxy, добавьте HTTPS и firewall. Без `DASHBOARD_ADMIN_TOKEN` изменяющие запросы и чтение паролей разрешены, поэтому такой запуск допустим только на localhost.

## Сценарии и автопроверки

Сценарий содержит выбранный QEMU-шаблон, bootstrap и отдельный autocheck-скрипт. Количество VM, начальный IPv4 с префиксом и bridge выбираются в мастере развёртывания; тип клона фиксирован как linked clone. Сохранённый код привязан к сценарию; стенд запускает актуальную версию автопроверки своего сценария.

Поле IPAM сохраняет адресную часть введённого CIDR. Поэтому `10.39.4.0/16` начинает выдачу с `10.39.4.0`, а не с нормализованного `10.39.0.0`. Пропускаются только настоящий адрес сети, broadcast и уже занятые адреса. Резервации создаются одной транзакцией до фонового клонирования, поэтому параллельные запросы не получают одинаковые IP. Ошибочный стенд сохраняет резервации до удаления, чтобы адрес случайно не был выдан работающей VM; при удалении стенда они освобождаются автоматически.

В редакторе bootstrap доступна кнопка **«Вставить из vklvikl»**. Она восстанавливает сетевой Linux-скрипт из исходного `vklvikl.py`: назначает переданный `VM_IP`, берёт префикс из `STAND_SUBNET`, обновляет `/etc/hosts` и без отключения интерфейса применяет конфигурацию через `ifreload`. Для старого `ifupdown` вместо потенциально конфликтного live-переключения backend автоматически один раз перезагружает только эту VM. По умолчанию используются гостевой интерфейс `vmbr0` и gateway `10.39.1.1`; их можно переопределить переменными `GUEST_INTERFACE` и `VM_GATEWAY`. Backend дополнительно проверяет `UP`, активный bridge-порт и единственный точный IP даже у ранее сохранённых сценариев со старой версией скрипта. Пароль `root` и snapshot `start` создаются только после этой проверки.

В карточке каждого развёрнутого стенда доступна кнопка **«Вернуть к изначальному состоянию»**. После подтверждения dashboard предварительно проверяет наличие завершённого snapshot `start` и сохранённого пароля у каждой VM, откатывает машины пакетами, запускает их, ждёт QEMU Guest Agent и повторно применяет сохранённые текущие пароли. Результаты прежней автопроверки сбрасываются как устаревшие. Операция удаляет все дисковые и конфигурационные изменения после `start` и выполняется в фоне со статусом «Восстанавливается». Если QEMU Guest Agent не подтвердил восстановление пароля отдельной VM, dashboard скрывает этот пароль как недостоверный, но сохраняет его внутри для безопасного повторного запуска операции. Для подключённых существующих pools кнопка остаётся недоступной, пока dashboard не располагает подтверждением snapshot `start` и сохранёнными доступами для каждой VM.

На странице **«Стенды»** кнопка **«Добавить существующий pool»** показывает pools из Proxmox, которые ещё не закреплены за стендами. При подключении выбирается сценарий, а найденные QEMU VM добавляются в мониторинг нагрузки и становятся доступны для действий стенда. Удаление такого подключения удаляет только запись дашборда: исходный pool, VM и диски в Proxmox сохраняются.

Фоновая синхронизация выполняется раз в 30 секунд без пересоздания страницы. Пока открытая карточка показывает развёртывание или автопроверку, она опрашивает только этот стенд примерно раз в секунду, незаметно обновляет прогресс и сохраняет прокрутку. Кнопка **«Обновить»** немедленно перерисовывает текущую страницу.

В live-режиме код передаётся через QEMU Guest Agent и выполняется **внутри гостевой VM**, а не на сервере дашборда:

- PowerShell определяется по заголовку и характерным конструкциям;
- остальные скрипты запускаются через `bash`;
- bootstrap имеет таймаут 900 секунд на VM;
- автопроверка имеет таймаут 180 секунд на VM и получает `VMID`;
- результаты каждой VM объединяются в один запуск.

Рекомендуемый формат stdout автопроверки — JSON, один объект на строку:

```json
{"name":"Служба DNS","ok":true,"message":"named active"}
{"name":"Маршрут","ok":false,"message":"default route missing"}
```

Также поддерживаются JSON-массив и короткие значения `name:ok`, `name:passed`, `name:fail`, `name:failed`, `name:error`. Итоговый статус: `passed` при результате от 90%, `warning` от 70%, иначе `failed`.

Скрипты считаются доверенным административным кодом. Встроенной песочницы, проверки синтаксиса и согласования изменений нет. Не помещайте в них токены, пароли и другие секреты: текст сценариев хранится в SQLite без шифрования.

## Как устроены метрики

В live-режиме backend получает `/cluster/resources` и сопоставляет ресурсы с VMID из таблицы `stand_vms`:

- общая CPU, RAM и disk-нагрузка вычисляется по ресурсам нод;
- экзаменационная нагрузка — сумма потребления работающих VM, принадлежащих управляемым стендам;
- `exam_cpu`, `exam_ram` и `exam_disk` показывают долю полной ёмкости кластера;
- `exam_*_share` показывает долю экзаменационных VM в текущем общем потреблении;
- по каждой ноде возвращаются общая нагрузка, вклад экзаменационных VM и их количество.

История live-метрик хранится только в памяти процесса: максимум 120 образцов, новый образец появляется при запросе метрик и исчезает после перезапуска. Результат `/cluster/resources` кэшируется на 5 секунд; при стандартном невидимом опросе frontend раз в 30 секунд история охватывает примерно час. В demo-режиме возвращается синтетический 24-часовой ряд.

Атрибуция является оценкой по телеметрии VM. Нагрузку гипервизора, общий page cache, shared storage, сетевую инфраструктуру и часть фонового I/O нельзя строго отнести к конкретному стенду. Значения CPU в карточках отдельных стендов сейчас хранятся в SQLite и не пересчитываются из Proxmox непрерывно; для оперативной картины используйте кластерные и понодовые показатели.

## Смена пароля стенда

Операция `rotate_password` доступна для запущенного стенда или отдельной VM и вызывает `set-user-password` QEMU Guest Agent. При deploy для каждой VM генерируется отдельный 16-символьный пароль. Системный пользователь по умолчанию — `root`, логин вложенного Proxmox web UI — `root@pam`.

Чтобы доступ можно было открыть после перезапуска dashboard, пароль хранится в SQLite и выдаётся только через защищённые маршруты `/credentials`. Обычные ответы `/stands` его не содержат, а тела ответов не логируются встроенным сервером. Ограничьте права на файл базы (`chmod 600 data/dashboard.db`), обязательно задайте `DASHBOARD_ADMIN_TOKEN`, используйте HTTPS и не логируйте тела ответов на reverse proxy.

Кнопка **«Перейти к стенду»** показывает трёхшаговый вход. Сначала оператор открывает адрес VM и один раз вручную принимает самоподписанный сертификат. Затем dashboard может отправить логин и пароль непосредственно в штатный HTML login endpoint этой VM, после чего интерфейс открывается с установленной Proxmox-сессией. Логин и пароль также копируются раздельно как надёжный запасной вариант; секреты не помещаются в URL.

Нативную страницу браузера **«Принять риск»** нельзя нажать из JavaScript. Старый `vklvikl` обходил её локальным Selenium с `--ignore-certificate-errors`, но серверный dashboard не управляет браузером оператора. Для полностью прозрачного одношагового входа установите доверенные сертификаты на вложенные Proxmox либо используйте отдельный reverse proxy/auth-bridge с DNS-именами стендов.

## Безопасность и ротация старого токена

Прежний API-токен находился непосредственно в исходном скрипте. Считайте его скомпрометированным, даже если файл больше не содержит секрета:

1. Создайте новый токен для отдельной служебной учётной записи и выдайте минимальные ACL.
2. Передайте новый секрет через `PROXMOX_TOKEN_VALUE`; не записывайте его в код, README или `.env.example`.
3. Запустите live-режим и проверьте `GET /api/health`.
4. Сразу отзовите старый токен в Proxmox: удалите его в `Datacenter → Permissions → API Tokens`.
5. Если секрет попадал в Git, артефакты CI, резервные копии или логи, очистите историю/артефакты и запустите secret scanning. Простого удаления строки из текущей версии недостаточно.

Дополнительные рекомендации:

- оставляйте `PROXMOX_VERIFY_SSL=true`; для собственного CA установите доверенный корневой сертификат на host дашборда;
- не публикуйте встроенный HTTP-сервер напрямую в интернет;
- используйте reverse proxy с HTTPS, полной аутентификацией и ограничением по сети;
- задавайте длинный случайный `DASHBOARD_ADMIN_TOKEN` и периодически меняйте его;
- не коммитьте рабочий `.env`, SQLite-базу, выгрузки паролей и логи;
- проверяйте deploy/autocheck-код перед публикацией сценария;
- перед удалением стенда убедитесь, что pool и VMID принадлежат именно ему: операция удаляет VM и диски без корзины.

## Основные API-маршруты

API принимает и возвращает JSON. Тело запроса должно быть JSON-объектом и не может превышать 2 МиБ. Если задан `DASHBOARD_ADMIN_TOKEN`, все `POST`, `PATCH`, `DELETE` и GET-маршруты `/credentials` требуют заголовок `X-Admin-Token`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | состояние сервера и интеграции Proxmox |

## Ограничения текущей версии

- Встроенный `ThreadingHTTPServer` предназначен для локальной эксплуатации и пилота; в production нужен reverse proxy, TLS и внешняя аутентификация.
- Полноценной модели пользователей и ролей dashboard пока нет. Административный токен защищает изменения и чтение паролей, но не остальные данные.
- Demo seed добавляется только в режиме `demo`; новая live-база начинается пустой, чтобы синтетические VMID не могли пересечься с реальными гостями.
- Фоновые deploy/check-задачи — daemon threads текущего процесса. После рестарта они не восстанавливаются автоматически, а записи могут остаться в `provisioning` или `running` до ручного исправления.
- Стенды бессрочные: автоматическая остановка или удаление по TTL намеренно отсутствует.
- Поддерживается развёртывание QEMU VM; LXC-сценарии в новом gateway не реализованы.
- QEMU Guest Agent обязателен для bootstrap, автопроверки и смены пароля.
- Пакетные операции над несколькими VM не атомарны. Перед `rollback_start` snapshot проверяется у всего стенда, но runtime-ошибка Proxmox всё равно может оставить часть уже откатившихся VM; dashboard покажет это как ошибку и не снимает защитные lock вручную.
- История live-метрик не сохраняется в SQLite и не является системой долговременного мониторинга.
- Редактор скриптов не предоставляет sandbox, lint, approval workflow и полноценную историю версий.
- Автовход через штатный HTML endpoint требует, чтобы сертификат VM уже был принят браузером и браузер разрешил её session cookie. Для гарантированного одношагового SSO нужен внешний auth-bridge или общий доверенный PKI.
