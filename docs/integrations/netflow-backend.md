# Стенды из личного кабинета Netflow: контракт для разработчика

Студент входит **только в Netflow**. Браузер работает с API этого же сайта. Deployer из локальной сети сам подключается к Netflow по HTTPS, забирает заявки и возвращает состояние. Сайт не подключается к БД Deployer или Proxmox; публиковать их в интернете не требуется. Фронтенд не входит в эту поставку.

## Три запроса для интерфейса

| Метод и путь на Netflow | Что передавать | Что вернётся при успехе (HTTP 200) |
| --- | --- | --- |
| `GET /api/me/stand/scenarios` | Текущая сессия сайта | `{"scenarios":[{"assignment_id":"lab-7-276"}]}` — доступные группе идентификаторы. Числа здесь и ниже — пример. |
| `POST /api/me/stand` | Та же сессия, JSON `{"assignment_id":"lab-7-276"}`, штатный заголовок сайта `X-CSRF-Token`, запрос с того же origin | `{"stand":{"job_id":"…","assignment_id":"lab-7-276","status":"queued","progress":0,"web_url":null}}`. Пока заявка активна, повтор для того же сценария возвращает её же. |
| `GET /api/me/stand` | Текущая сессия | Та же структура с актуальным состоянием; `{"stand":null}`, если стенда нет. |

При открытии страницы запросите список сценариев и текущий стенд. Покажите «Развернуть» только для разрешённого сценария. После нажатия опрашивайте **GET**, например раз в 5 секунд, пока вкладка видна; при возвращении во вкладку запросите состояние сразу. После сетевой ошибки при POST сначала запросите состояние: сервер мог уже принять заявку. Один студент может занимать один стенд, независимо от количества вкладок или устройств. Список сценариев пока содержит только ID, не Markdown, картинки или названия.

| `status` | Что показать |
| --- | --- |
| `queued` / `building` | В очереди / идёт развёртывание. Поле `progress` — число от 0 до 100. |
| `awaiting_confirmation` | Задача приостановлена, требуется действие преподавателя в Deployer. |
| `ready` | Стенд готов. Показывайте «Войти в стенд» **только если** в этом же ответе есть непустой `web_url`. |
| `verifying` | Нет свежего подтверждения готовности. Не показывайте старую ссылку даже при 100%. |
| `rejected` | Заявка отклонена **до создания VM**, например не хватило адресов. Последний такой отказ виден до 24 часов. Слот свободен: предложите «Попробовать ещё раз», не повторяйте POST автоматически. |
| `stopped` / `expired` / `error` | Остановлен / истекло время / ошибка. Не заказывайте новую VM автоматически. |

При подтверждённом удалении ответ меняется на `{"stand":null}`. Ссылку нельзя выводить из ID, сохранять между сессиями или подставлять из предыдущего ответа. Даже при `ready` она может быть отключена политикой. В разрешённом варианте это HTTPS-адрес **гостевого** Proxmox в сети `10.39.0.0/16`, порт 8006, а не адрес управления кластером. Открывайте в новой вкладке с `rel="noopener noreferrer"`. Это не автоматический вход: API не передаёт пароль VM или ключ VPN. Сбросьте состояние интерфейса при выходе/смене пользователя и при отказе в доступе.

Ошибки: `{"error":"…"}`. При **400** проверьте тело запроса; **401** — нужна сессия; **403** — проверьте CSRF, временный пароль, состояние учётки и доступ группы; **404** — маршрут выключен или отсутствует; **409** — у студента уже есть другой стенд, который должен освободить преподаватель; **503** — интеграция не настроена. При сбое сервера или сети покажите отсутствие связи и повторяйте чтение с увеличивающейся задержкой. Не отправляйте с клиента логин, группу, ID студента, адрес VM или служебный ключ.

## Как подключить на тестовом окружении

1. **Netflow.** Сделайте резервную копию БД и проверьте версию исходника. В каталоге с `app.py` на **тестовой копии** выполните `git apply --check <путь-к-app.py.patch>`, затем `git apply <путь-к-app.py.patch>`. Скопируйте рядом модули [stand_routes.py](../../integrations/netflow/stand_routes.py) и [stand_queue.py](../../integrations/netflow/stand_queue.py). [Сам патч](../../integrations/netflow/app.py.patch) подключает маршруты к существующему обработчику сессии и CSRF; при расхождении версий не заменяйте весь файл. Навигационный HTML-патч из более раннего прототипа не нужен.
2. **Сценарий.** В Deployer выберите активное опубликованное задание с шаблоном и нужной группой. Формат идентификатора: `lab-<ID сценария Deployer>-<VMID шаблона>`. В окружении процесса **Netflow** задайте `NETFLOW_STANDS_ENABLED=1`, `NETFLOW_STAND_SCENARIOS={"lab-7-276":["SSA-25-04"]}` (заменить на реальные значения) и `NETFLOW_WORKER_TOKEN`. Ключ — новый случайный секрет, например результат `secrets.token_urlsafe(32)`, одинаковый **только у двух серверов**. Не помещайте его в JavaScript, Git или журналы. После изменения карты групп перезапустите процесс Netflow.
3. **Deployer.** Нужны рабочий live-режим, защита административным токеном и выделенный диапазон `STUDENT_LAB_IP_START`–`STUDENT_LAB_IP_END` внутри `10.39.0.0/16`. В окружении процесса задайте `NETFLOW_INTEGRATION_URL` равным HTTPS-origin тестового Netflow, без пути; `NETFLOW_WORKER_TOKEN` — тот же отдельный ключ. Для будущего подключения к рабочему сайту origin — `https://cite.netflow59.ru`. Входящие подключения к Deployer для этой интеграции не нужны. Не отключайте проверку сертификата.
4. **Вход в VM.** По умолчанию `NETFLOW_ALLOW_LAB_LINKS=0`: статусы передаются без адресов. Включайте значение `1` только после проверки маршрута со студенческого устройства и правил, разрешающих студенту доступ **к своей VM, а не ко всей подсети**. Выдача или отзыв VPN, гостевых паролей и активных сеансов Proxmox — отдельная задача. Блокировка учётки сайта не отзывает сетевой доступ сама по себе.
5. **Приёмка.** С двумя обычными тестовыми учётками проверьте публикацию для одной группы, повторный клик, отключение и возврат связи, отсутствие чужого стенда и ссылки после блокировки. Первую реальную VM разворачивайте только на согласованном тестовом шаблоне. Для остановки обмена установите на Netflow `NETFLOW_STANDS_ENABLED=0`, на Deployer очистите URL и служебный ключ, установите флаг ссылок в `0` и перезапустите процессы. Это не удаляет очереди, стенды или пользователей.

## Служебный обмен

Только Deployer вызывает `POST /api/integration/jobs/claim` с `{}` и `POST /api/integration/jobs/status` с `job_id`, `lease_token`, `status`, `progress` и при необходимости `web_url`. Оба запроса используют JSON и `Authorization: Bearer …`; cookie браузера не принимаются. Секрет работника отделён от токенов администратора и Proxmox. Не включайте журналирование заголовка авторизации, тел этих запросов или ответов.

Netflow — источник пользователей и групп. Для связи серверы используют отдельный постоянный идентификатор, не логин и не голый числовой ID: переименование не теряет стенд, а повторное использование ID удалённой учётки не передаёт чужой стенд новому студенту. Вторая студенческая учётка в Deployer не создаётся. Deployer дополнительно проверяет локальную публикацию сценария и права группы перед созданием VM и выдачей ссылки.

Очередь отдаёт заявку во временное владение (90 секунд). Просроченный отчёт не принимается. При повторной доставке Deployer сверяет сохранённую привязку и не выделяет вторую VM. Источник состояния — существующий механизм студенческих стендов; нормальный интервал повторной проверки — 10 секунд, через 60 секунд без подтверждения Netflow скрывает прежнюю ссылку. При отзыве прав служебная сверка не останавливает/не удаляет VM. Если сверка уже зафиксировала отзыв для существующей VM, простая разблокировка не выдаст её снова: преподавателю нужно проверить и освободить прежний стенд.

Локальные проверки без кластера: `python -m unittest discover -s tests -p "test_netflow*.py"` из корня Deployer. Для конкретной версии сайта: `python integrations/netflow/check_host.py <путь-к-проверенной-копии-app.py>`. Этот тест применяет патч к временному файлу и проверяет настоящие обработчики сессий сайта на вымышленных пользователях; ему не требуется доступ к рабочей БД.
